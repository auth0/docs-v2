The Cross App Access (XAA) standard is a [draft IETF specification](https://datatracker.ietf.org/doc/draft-ietf-oauth-identity-assertion-authz-grant/)
that enables applications to obtain an access token for a third-party API without needing the end 
user to sign into the third-party app and approve the application's access. Instead, that access is
mediated by a centralized identity provider (IdP) that is trusted by both your organization and the
third-party API.

In a workplace environment, IT admins would often prefer to manage which applications employees have
access to and which applications are connecting to each other's APIs, rather than employees
connecting accounts and approving information sharing individually. The XAA specification allows
that to happen, and Token Vault can use this approach to obtain access tokens, while exposing those
access tokens to your applications and AI Agents through its existing API, meaning you write the 
code once, and it works with either Connected Accounts or XAA.

## What's different with XAA?

1. When using Token Vault with XAA, end users do not need to [connect their account](/docs/secure/call-apis-on-users-behalf/token-vault/connected-accounts-for-token-vault)
with external applications. Your application does not need to provide a button to "Connect to 
[Third-party Application]" that makes a POST request to the My Account API's 
`/me/v1/connected-accounts/connect` endpoint.
2. XAA depends on the end user having authenticated using a federated login with an Okta or OIDC
connection that is configured for XAA. That connection must be configured as a "Requesting 
Application" (read [Configuring the Requesting App Connection](#1-configuring-the-requesting-app-connection)
for details).
3. The third-party API being accessed must support XAA as a "Resource App", meaning it can exchange
an `ID-JAG` for access tokens. Third-party applications that are also using Auth0 can enable this
feature; read [Cross App Access (XAA)](/docs/secure/call-apis-on-users-behalf/xaa) for details.
4. A connection to the third-party application must exist with Connected Accounts for Token Vault
and Cross App Access for Token Vault enabled. (Read [Configuring the Resource App 
Connection](#2-configuring-the-resource-app-connection) for details.)

## Configuring Token Vault with XAA

### 1. Configuring the Requesting App Connection

#### 1.a. Enable Cross App Access, Requesting App

Both Okta and OIDC connection types can be configured to act as XAA Requesting Applications. To 
enable, open the Connection details in the management dashboard, scroll down to the Cross App 
Access section and turn on the *Requesting Application* toggle.

<Frame>![Cross App Access section of a connection's settings, with the Requesting Application toggle turned on](/docs/images/xaa/xaa_connection_requesting_app.png)</Frame>

#### 1.b. Request a Refresh Token

Add `offline_access` to the *Scopes* field. Token Vault requires a Refresh Token from the IdP in
order to request an `ID-JAG`. You must therefore check that the connection requests one. You may 
also need to modify the configuration of your IdP to ensure a Refresh Token is issued when a user
logs in.

**For Okta Connections** select *Use a template* -> *Okta Basic* and add `offline_access` to the 
`userinfo_scope` list in the JSON mapping.

<Frame>![JSON user mapping for an Okta connection, with offline_access added to the userinfo_scope list](/docs/images/xaa/xaa_okta_user_mapping.png)</Frame>

#### 1.c. Ensure Communication Channel is set to Back Channel 

Visit the *Credentials* tab and check the *Communication Channel* is set to *Back Channel*. Token
Vault cannot request an `ID-JAG` using the Front Channel.

#### Management API

Alternatively, use the Management API to set the `cross_app_access_requesting_app.active` property 
to `true` on the connection, and configure the `offline_access` scope and the user mapping:

```bash lines
PATCH https://{yourDomain}/api/v2/connections/{yourConnectionId}
Authorization: Bearer <YOUR_MANAGEMENT_API_ACCESS_TOKEN>
Content-Type: application/json
{
  "cross_app_access_requesting_app": { "active": true },
  "options": {
    "scope": "openid profile email offline_access"
  },
  "type": "back_channel",
  "attribute_map": {
    "attributes": {
      "name": "${context.tokenset.name}",
      "email": "${context.tokenset.email}",
      "username": "${context.tokenset.preferred_username}",
      "federated_groups": "${context.userinfo.groups}",
      "federated_locale": "${context.userinfo.locale}",
      "federated_zoneinfo": "${context.userinfo.zoneinfo}"
    },
    "mapping_mode": "use_map",
    "userinfo_scope": "openid email profile groups offline_access"
  }
}
```

The next time a user signs in using that connection, Token Vault will retain the Refresh Token,
and this can be used to request access to a third-party API.

### 2. Configuring the Resource App Connection

To enable Token Vault to use XAA to request access tokens for a third-party API, create or edit a 
connection to that third-party API's authorization server.

#### 2.a. Enable Connected Accounts for Token Vault

This step enables Token Vault for a particular connection, and is the same as when not using XAA. 
On the connection's settings tab, find the *Purpose* section and select either "Connected Accounts 
for Token Vault" or "Authentication and Connected Accounts for Token Vault".

<Frame>![Purpose section of a connection's settings tab, with Connected Accounts for Token Vault selected](/docs/images/token-vault/enable_connected_account_purpose.png)</Frame>

#### 2.b. Enable Cross App Access for Token Vault

Next, scroll down to the Cross App Access section and turn on the *Enable Cross App Access for Token
Vault* setting:

<Frame>![Cross App Access section of a connection's settings, with Enable Cross App Access for Token Vault turned on](/docs/images/xaa/xaa_connection_token_vault.png)</Frame>

#### Management API

Alternatively, use the Management API to set the `connected_accounts.active` and 
`connected_accounts.cross_app_access` properties to `true` on the connection:

```bash lines
PATCH https://{yourDomain}/api/v2/connections/{yourConnectionId}
Authorization: Bearer <YOUR_MANAGEMENT_API_ACCESS_TOKEN>
Content-Type: application/json
{
  "connected_accounts": { 
    "active": true,
    "cross_app_access": true
  } 
}
```

### 3. Call Token Vault as Usual

You can now call Token Vault as you normally would, for the Resource App Connection:

```bash lines
curl --request POST 'https://{yourDomain}/oauth/token' \
--header 'Content-Type: application/json' \
--data '{
  "client_id": "<YOUR_CLIENT_ID>",
  "client_secret": "<YOUR_CLIENT_SECRET>",
  "grant_type": "urn:auth0:params:oauth:grant-type:token-exchange:federated-connection-access-token",
  "subject_token": "<YOUR_AUTH0_REFRESH_TOKEN>",  
  "subject_token_type": "urn:ietf:params:oauth:token-type:refresh_token",
  "requested_token_type": "http://auth0.com/oauth/token-type/federated-connection-access-token",
  "connection": "<YOUR_RESOURCE_APP_CONNECTION>"
}'
```

In the background, Token Vault will use the XAA flow to obtain those access tokens, 
meaning that it will look for a stored Refresh Token from a valid Requesting App IdP, ask that IdP 
for an `ID-JAG` token on your behalf, and then present it to the `Resource App` in exchange for
an access token, before returning the access token to your app.

### Handling Multiple Requesting App IdPs

An Auth0 tenant might have many connections configured to IdPs that support XAA as a Requesting App,
and which have XAA enabled (e.g. their `cross_app_access_requesting_app.active` property is set to
`true`). 

When a Token Vault request is made, the actual IdP to request an `ID-JAG` from depends on which IdPs
the user has and signed in to. There must be exactly one valid user identity linked to the current 
user's profile, and with XAA enabled, otherwise Token Vault will not know which IdP to request an
`ID-JAG` from. If there are multiple valid identities, the request will fail because it is unclear 
which IdP to call. The response will be:

```json
{
    "error": "invalid_request",
    "error_description": "Multiple enterprise connections with XAA support enabled"
}
```

If the current user profile has more than 10 linked identities on connection types that support XAA 
(i.e. Okta and OIDC connection types) *even if those connections do not have XAA enabled* Token
Vault will fail with the error:

```json
{
    "error": "invalid_request",
    "error_description": "User can have a maximum of 10 linked accounts to use XAA"
}
```

This limits the number of connections that Token Vault must check in order to locate a valid XAA
connection.

#### Using Auth0 Organizations with XAA

Token Vault will also filter the available Requesting App connections by those that are enabled for 
the current user's organization. An Auth0 solution that uses Organizations can limit access to each 
IdP by Organization in order to clarify which Requesting App connection should be used for each 
user session.

Each `subject_token` that is used in a Token Vault exchange contains information about the 
organization that the user logged into. This organization context will be used to find the correct
XAA Requesting App connection. However, if multiple valid connections are found, the request will 
still fail.
