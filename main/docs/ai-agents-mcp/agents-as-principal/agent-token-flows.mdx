Once [associated with a machine-to-machine (M2M) client](/docs/ai-agents-mcp/agents-as-principal/associate-agent-m2m-client), tokens issued by that client will have the agent's identity for attribution and traceability in logs. Agent-linked clients support the following authentication and authorization flows:
- [Standard login flow](/docs/ai-agents-mcp/agents-as-principal/agent-token-flows#flow-1-standard-login-flow): The agent-linked client authenticates via authorization code, implicit, CIBA, device, MFA, password, passkey, or refresh token grant.
- [Client Credentials flow](/docs/ai-agents-mcp/agents-as-principal/agent-token-flows#flow-2-client-credentials-flow): The agent-linked client authenticates as the agent (`sub` claim is the agent ID or `external_agent_id`)
- [On-Behalf-Of (OBO) token exchange](/docs/ai-agents-mcp/agents-as-principal/agent-token-flows#flow-3-obo-token-exchange): The agent-linked client performs a token exchange in a delegated access flow. 

## Agent entity profile claims

Auth0 adopts the [OAuth Actor Profile for Delegation](https://www.ietf.org/archive/id/draft-mcguinness-oauth-actor-profile-00.html) draft, introducing `sub_profile` and `client_profile` claims to specify the entity type in tokens issued by agent-linked clients:

| Claim | Description |
|---|---|
| `sub_profile` | Entity type of the subject. Values: `user`, `ai_agent`, `service`, `browser_app`, `native_app`. |
| `client_profile` | Entity type of the requesting client. Same value set as `sub_profile`. Multiple space-separated values permitted (for example, `service ai_agent`). |
| `act` | Actor claim for the OBO token exchange. Present whenever an agent-linked client is involved. Contains `sub`, `iss`, `sub_profile`, `client_id`, `client_profile`, and optionally `cnf` (DPoP binding) and a nested `act` for multi-hop chains. |

`sub_profile` and `client_profile` are issued when [enabled on the resource server](#configure-resource-server-to-receive-agent-entity-profile-claims). They appear at the top level and inside each `act` node. Wherever an agent's ID appears in a claim (top-level `sub` or `act.sub`), it is the agent's `external_agent_id` if one was set at creation. Otherwise, it is the `agent_id`.

<Callout icon="file-lines" color="#0EA5E9" iconType="regular">
**Breaking changes.** Two distinct breaking changes apply when you associate clients with agents:

1. **Agents as subjects.** For client credentials grants, the `sub` claim can contain an agent ID (`agt_72jbvv7LfRKYp59gtRLtkn`, or a customer-supplied `external_agent_id`) rather than a user or M2M client identifier. Any service that validates, parses, or stores `sub`, including authorization checks, audit pipelines, and user lookup logic, must handle this new format.

2. **`sub_profile` claim.** The new `sub_profile` claim introduces a formal entity type into the token. Services that receive tokens should not assume `sub_profile` will always be `user`. If `sub_profile` is absent (resource server opt-in is not enabled), existing behavior remains unchanged.

Review all downstream `sub` consumers before associating clients with agents or enabling entity profile claims on a resource server.
</Callout>

## Configure resource server to receive agent entity profile claims

To receive `sub_profile` and `client_profile` claims, set `agent_subject_claims: 'auth0-v1'` on the target resource server configuration. This is opt-in per resource server.

**Example:**

```http
PATCH /api/v2/resource-servers/{id}
Content-Type: application/json

{
  "agent_subject_claims": "auth0-v1"
}
```

<Callout icon="file-lines" color="#0EA5E9" iconType="regular">
Review `sub` parsing in downstream services before enabling. Services that validate or parse the `sub` claim format may need updates to handle `ai_agent` as a valid entity type.
</Callout>

## Flow 1: Standard login flow

An agent-linked client can also be the client of a standard login (authorization code, implicit, CIBA, device, MFA, password, passkey, or refresh token grant) rather than performing token exchange. In this case, the subject is still the user, and the top-level claims do not carry the agent ID. Instead, a single-level `act` claim is added so the agent is identifiable in the token:

```json
{
  "iss": "https://YOUR_DOMAIN/",
  "sub": "auth0|user123",
  "sub_profile": "user",
  "client_id": "agent-linked-client-id",
  "client_profile": "ai_agent",
  "aud": "https://resource-api.example.com",
  "scope": "read:data",
  "exp": 1711820400,
  "iat": 1711816800,
  "act": {
    "sub": "agt_1a2b3c",
    "sub_profile": "ai_agent",
    "client_id": "agent-linked-client-id"
  }
}
```

## Flow 2: Client credentials flow

An agent-linked M2M client performs a standard client credentials grant. The agent is the subject and authenticates as itself.

**Issued token:**

```json
{
  "iss": "https://YOUR_DOMAIN/",
  "sub": "agt_1a2b3c",
  "sub_profile": "ai_agent",
  "client_id": "YOUR_CLIENT_ID",
  "client_profile": "service ai_agent",
  "aud": "https://your-resource-api.example.com",
  "scope": "read:data",
  "exp": 1711820400,
  "iat": 1711816800
}
```

## Flow 3: OBO Token exchange

The user authenticates and receives an access token scoped to the agent resource server as the audience. The agent-linked client exchanges this for a delegated token using the [On-Behalf-Of Token Exchange](/docs/secure/call-apis-on-users-behalf/on-behalf-of-token-exchange).

Before the token exchange, the user access token has the following claims: 
- the `sub` claim is the user ID
- the `sub_profile` is of type `user`
- the `client_profile` identifies the client as a `browser_app`
- the `aud` claim is to the agent resource server 

**User access token (before exchange):**

```json
{
  "iss": "https://YOUR_DOMAIN/",
  "sub": "auth0|user123",
  "sub_profile": "user",
  "client_id": "spa-client-id",
  "client_profile": "browser_app",
  "aud": "https://ai-agent-resource-server.example.com",
  "scope": "read:data",
  "exp": 1711820300,
  "iat": 1711816700
}
```
After the token exchange, the exchanged access token has the following claims:
- the `sub` claim remains the user ID
- the `sub_profile` remains of type `user`
- the `client_profile` is now of type `service` and `ai-agent` representing the agent and the M2M client that the agent is linked to that performed the token exchange
- the `aud` claim is scoped to the new resource server
- the `act` claim shows the immediate actor, which is the agent (`"sub": "agt_1a2b3c", "sub_profile": "ai_agent",`) and its nested `act`, which shows the original client that initiated the flow. Maximum depth is 5 hops (4 nested `act` levels).

**Step 3 — Token after exchange:**

```json
{
  "iss": "https://YOUR_DOMAIN/",
  "sub": "auth0|user123",
  "sub_profile": "user",
  "client_id": "agent-client-id",
  "client_profile": "service ai_agent",
  "aud": "https://resource-api.example.com",
  "scope": "read:data",
  "cnf": { "jkt": "NzbLsXh8uDCcd7MNwrnNZpX0ak8ACQ" },
  "exp": 1711820400,
  "iat": 1711816800,
  "act": {
    "sub": "agt_1a2b3c",
    "sub_profile": "ai_agent",
    "client_id": "agent-client-id",
    "act": {
      "sub": "spa-client-id",
      "sub_profile": "browser_app",
      "client_id": "spa-client-id"
    }
  }
}
```

<Callout icon="file-lines" color="#0EA5E9" iconType="regular">
Refresh tokens are not supported for the OBO token exchange. To learn more about the OBO token exchange, including setup and limitations, read [On-Behalf-Of Token Exchange](/docs/secure/call-apis-on-users-behalf/on-behalf-of-token-exchange).
</Callout>

## Known limitations

- **`jwt_bearer` grant**: Not yet supported for agent-linked clients.
- **Agent or client as top-level OBO subject**: Token exchange currently supports OBO only when the subject of the incoming token is a user. Issuing tokens where an agent or a client is itself the top-level subject of an OBO exchange is not yet supported.
