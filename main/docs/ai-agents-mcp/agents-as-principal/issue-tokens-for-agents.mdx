Agents support [RFC 8693](https://datatracker.ietf.org/doc/html/rfc8693) token exchange for delegation flows. Auth0 adopts the **OAuth Actor Profile for Delegation** draft, introducing `sub_profile` and `client_profile` claims to explicitly specify the entity type in issued tokens.

## Token claims reference

| Claim | Description |
|---|---|
| `sub_profile` | Entity type of the subject. Values: `user`, `ai_agent`, `service`, `browser_app`, `native_app`. |
| `client_profile` | Entity type of the requesting client. Same value set. Multiple space-separated values permitted (for example, `service ai_agent`). |
| `act` | Actor claim per RFC 8693. Present whenever an agent-linked client is involved. Contains `sub`, `iss`, `sub_profile`, `client_id`, `client_profile`, and optionally `cnf` (DPoP binding) and a nested `act` for multi-hop chains. |

`sub_profile` and `client_profile` are issued when enabled on the resource server configuration. They appear at the top level and inside each `act` node. Wherever an agent's ID appears in a claim (top-level `sub` or `act.sub`), it is the agent's `external_agent_id` if one was set at creation, otherwise the `agent_id`.

<Callout type="warning">
**Breaking changes.** Two distinct breaking changes apply when you associate clients with agents:

1. **Agents as subjects.** For client credentials grants, the `sub` claim can contain an agent ID (`agt_72jbvv7LfRKYp59gtRLtkn`, or a customer-supplied `external_agent_id`) rather than a user or M2M client identifier. Any service that validates, parses, or stores `sub` — including authorization checks, audit pipelines, and user lookup logic — must handle this new format.

2. **`sub_profile` claim.** The new `sub_profile` claim introduces a formal entity type into the token. Services that receive tokens should not assume `sub_profile` will always be `user`. If `sub_profile` is absent (resource server opt-in is not enabled), existing behavior remains unchanged.

Review all downstream `sub` consumers before associating clients with agents or enabling entity profile claims on a resource server.
</Callout>

## Flow 1: Client credentials (agent acting as itself)

An agent-linked M2M client performs a standard client credentials grant. The agent is the subject.

**Issued token:**

```json
{
  "iss": "https://YOUR_DOMAIN/",
  "sub": "agt_1a2b3c",
  "sub_profile": "ai_agent",
  "client_id": "YOUR_CLIENT_ID",
  "client_profile": "service ai_agent",
  "aud": "https://your-resource-api.example.com",
  "scope": "read:data",
  "exp": 1711820400,
  "iat": 1711816800
}
```

## Flow 2: Token exchange — On-Behalf-Of (OBO)

The user authenticates and receives an access token scoped to the agent resource server. The agent exchanges this for a delegated token using the [On-Behalf-Of Token Exchange](/docs/secure/tokens/access-tokens/token-exchange).

The following conditions must **all** be met for a successful token exchange:

| Requirement | Configuration |
|---|---|
| Client is confidential | Must authenticate with credentials (`client_secret` or `private_key_jwt`). |
| Client is first-party | `is_first_party: true` on the client. |
| Client is OIDC conformant | `oidc_conformant: true` on the client. |
| Client is a Custom API Client | `resource_server_id` must be set on the client. |
| OBO profile enabled on client | `token_exchange.allow_any_profile_of_type` includes the OBO profile type. |
| Target resource server allows skipping consent | `skip_consent_for_verifiable_first_party_clients: true` on the target resource server. |

**Step 1 — User access token (before exchange):**

```json
{
  "iss": "https://YOUR_DOMAIN/",
  "sub": "auth0|user123",
  "sub_profile": "user",
  "client_id": "spa-client-id",
  "client_profile": "browser_app",
  "aud": "https://ai-agent-resource-server.example.com",
  "scope": "read:data",
  "exp": 1711820300,
  "iat": 1711816700
}
```

**Step 2 — Token exchange request:**

```http
POST /oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=<user-access-token>
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&audience=https://resource-api.example.com
&client_id=agent-client-id
&client_secret=...
```

**Step 3 — Token after exchange:**

```json
{
  "iss": "https://YOUR_DOMAIN/",
  "sub": "auth0|user123",
  "sub_profile": "user",
  "client_id": "agent-client-id",
  "client_profile": "service ai_agent",
  "aud": "https://resource-api.example.com",
  "scope": "read:data",
  "cnf": { "jkt": "NzbLsXh8uDCcd7MNwrnNZpX0ak8ACQ" },
  "exp": 1711820400,
  "iat": 1711816800,
  "act": {
    "sub": "agt_1a2b3c",
    "sub_profile": "ai_agent",
    "client_id": "agent-client-id",
    "act": {
      "sub": "spa-client-id",
      "sub_profile": "browser_app",
      "client_id": "spa-client-id"
    }
  }
}
```

The outer `sub` remains the user. The `act` chain shows the immediate actor (agent) and its nested `act`, which shows the original client that initiated the flow. This enables full delegation chain traceability at any resource server.

## Flow 3: Agent-linked client on a standard login

An agent-linked client can also be the client of a standard login (authorization code, implicit, CIBA, device, MFA, password, passkey, or refresh token grant) rather than performing token exchange. In this case the subject is still the user, and the top-level claims do not carry the agent ID. Instead, a single-level `act` claim is added so the agent is identifiable in the token:

```json
{
  "iss": "https://YOUR_DOMAIN/",
  "sub": "auth0|user123",
  "sub_profile": "user",
  "client_id": "agent-linked-client-id",
  "client_profile": "ai_agent",
  "aud": "https://resource-api.example.com",
  "scope": "read:data",
  "exp": 1711820400,
  "iat": 1711816800,
  "act": {
    "sub": "agt_1a2b3c",
    "sub_profile": "ai_agent",
    "client_id": "agent-linked-client-id"
  }
}
```

## OBO constraints

- Refresh tokens are **not** supported for OBO grants.
- `act` nesting supports multi-hop agent chains (agent A delegating to agent B). Maximum depth is 5 hops (4 nested `act` levels).

## Known limitations

- **`jwt_bearer` grant**: Not yet supported for agent-linked clients.
- **Agent or client as top-level OBO subject**: Token exchange currently supports OBO only when the subject of the incoming token is a user (see Flow 2). Issuing tokens where an agent or a pure client is itself the top-level subject of an OBO exchange is not yet supported and is on the roadmap.
