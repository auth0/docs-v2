To ensure undisrupted service, see below to help troubleshoot any issues associated with an Auth0 Teams membership.

# Add a missing tenant

If you are on a self-service subscription plan and you don’t see a tenant under your Teams instance, verify the [subscription](/docs/troubleshoot/customer-support/manage-subscriptions) details:

1. First verify the [subscription](/docs/troubleshoot/customer-support/manage-subscriptions) details by checking the tenant's subscription.
2. Attempt to link the tenant by following the [Link tenants](/docs/get-started/auth0-teams/tenant-management) guide.

If the subscriptionis an Enterprise Agreementbut is not part of your Teams instance, contact [Auth0 Support](http://support.auth0.com) to assist in adding the tenant.

# Remove an unrecognized admin

If a Tenant administrator is listed as part of a tenant and should not be:

1. If you are a Team Owner and also the tenant admin for the tenant, access the Auth0 Dashboard for the tenant to remove the admin. To learn more, read [Team Member Management](/docs/get-started/auth0-teams/team-member-management).
2. Request a tenant administrator to remove the admin from the tenant.

# Troubleshoot connections

### SSO connection not appearing on the login page

If your SSO connection is not appearing on the login page, go to **Edit Connection** and ensure **Show as Button** is enabled.

### Domain verification stuck or failing

If your domain verification is stuck or failing, try the following:

- **Check the TXT record value** — ensure it was copied exactly with no extra spaces or characters.
- **Verify the record was added to the correct domain** — confirm it was added to the right DNS provider and domain.
- **Confirm the TXT record is publicly visible** — use a DNS lookup tool such as `dig` or an online DNS checker to verify the record is propagated before clicking **Verify**.
- **Check for conflicting TXT records** — some DNS providers do not allow duplicate TXT records. Remove any conflicts and retry.
- **Wait for DNS propagation** — DNS changes can take up to 48 hours to propagate, though they typically process faster. If verification fails, wait and retrigger verification.
- **Contact your DNS provider** — if the issue persists, your DNS provider may have specific formatting requirements or extended propagation delays.

### HRD not routing users correctly

If HRD is not routing users correctly, check the following:

- **User entering wrong email domain** — the email domain entered must exactly match the verified domain.
- **Multiple connections for the same domain** — if more than one connection is tied to the same domain, it may cause routing conflicts. Ensure only one connection is associated per domain.
- **HRD not enabled** — confirm the HRD toggle is turned on for the domain or connection.

### Missing or invalid email claim

If authentication fails after setting up an SSO connection, Auth0 may not be receiving a valid email address from your identity provider. Auth0 accepts a valid email address in either of these forms:

- The **NameID**, if it is set to an email format (for example, `user@company.com`)
- A **separate email attribute** explicitly mapped in the assertion

The error occurs when neither is present, or when the NameID is set to a non-email value such as a plain username.

#### Custom OIDC

Verify that the `email` scope is requested and that your IdP returns an `email` claim in the ID token. You can decode the ID token (for example, using [jwt.io](https://jwt.io)) to confirm the claim is present.

#### Custom SAML

Check whether your NameID is set to an email address. If it is, Auth0 will use it. If your NameID is set to a username or another non-email value, add an explicit `email` attribute in your IdP's attribute mapping configuration.

#### ADFS

Confirm that the outgoing claim sent to Auth0 contains a valid email address — either via the NameID (if configured to email format) or a separate email claim using the claim type `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress`. Verify the rule is applied to the relying party trust for Auth0.

#### Azure AD

Confirm that Auth0 receives a valid email address. If your users' UPN is in email format, this is typically sufficient. If not, add the `email` optional claim under **Optional claims** for the ID token in the enterprise application's token configuration.

#### Okta

Check the NameID format in your Okta application's **Sign On** settings. If NameID is set to a value in email format (for example, `user.email` or `user.login` where login is an email), the connection will work without a separate attribute statement. If NameID is set to a non-email value, add an attribute statement mapping `email` to `user.email`.

### Users locked out after enabling Enforce SSO

If team members are locked out after enabling Enforce SSO, contact [Auth0 Support](https://support.auth0.com/center/s/) for assistance.
