Le fichier de données utilisateur utilisé pour l’importation en bloc d’utilisateurs doit être au format JSON. Il doit contenir un tableau d’objets utilisateur correspondant au schéma indiqué.

<div id="user-json-schema">
  ## Schéma JSON des utilisateurs
</div>

<div id="user-object-properties">
  ## Propriétés de l’objet `user`
</div>

<ResponseField name="app_metadata" type="object" post={ [ "upsertable" ] }>
  Données pouvant influer sur les fonctionnalités de base de l’application ou sur les ressources auxquelles l’utilisateur peut accéder. Les données stockées dans `app_metadata` ne peuvent pas être modifiées par les utilisateurs. Elles peuvent notamment comprendre des plans de soutien, des rôles ou des groupes d’accès.

  Pour en savoir plus sur les métadonnées, consultez [Comprendre le fonctionnement des métadonnées dans les profils utilisateur](/docs/fr-ca/manage-users/user-accounts/metadata).

  <Expandable title="propriétés interdites">
    `app_metadata` ne peut pas contenir les propriétés suivantes :

    * `__tenant`
    * `_id`
    * `blocked`
    * `clientID`
    * `created_at`
    * `email_verified`
    * `email`
    * `globalClientID`
    * `global_client_id`
    * `identities`
    * `lastIP`
    * `lastLogin`
    * `loginsCount`
    * `metadata`
    * `multifactor_last_modified`
    * `multifactor`
    * `updated_at`
    * `user_id`
  </Expandable>
</ResponseField>

  Indique si l’utilisateur a été bloqué.
</ResponseField>

</ResponseField>

</ResponseField>

</ResponseField>

<ResponseField name="given_name" type="string" post={ ["upsertable"] }>
  Le prénom de l’utilisateur.
</ResponseField>

<ResponseField name="name" type="string" post={ ["upsertable"] }>
  Le nom complet de l’utilisateur.
</ResponseField>

<ResponseField name="nickname" type="string" post={ ["upsertable"] }>
  Le surnom de l’utilisateur.
</ResponseField>

<ResponseField name="picture" type="string" post={ ["upsertable"] }>
  URL de la photo de profil de l’utilisateur.
</ResponseField>

<ResponseField name="phone_number" type="string">
  Le numéro de téléphone de l’utilisateur. Il doit être au format E.164, y compris l’indicatif de pays, par exemple `+12125550001`.
</ResponseField>

<ResponseField name="phone_verified" type="boolean" default={false}>
  Indique si l’utilisateur a vérifié son numéro de téléphone.
</ResponseField>

<ResponseField name="user_id" type="string">
  L’identifiant unique de l’utilisateur. Il est précédé de la stratégie de connexion.
</ResponseField>

<ResponseField name="user_metadata" type="object" post={ ["upsertable"] }>
  Données qui n’ont aucune incidence sur les ressources auxquelles les utilisateurs peuvent accéder, comme l’adresse professionnelle, l’adresse domiciliaire ou les préférences de l’utilisateur.

  Pour en savoir plus sur les métadonnées, consultez [Comprendre le fonctionnement des métadonnées dans les profils utilisateur](/docs/fr-ca/manage-users/user-accounts/metadata).
</ResponseField>

<ResponseField name="username" type="string">
  Le nom d’utilisateur de l’utilisateur.
</ResponseField>

<ResponseField name="password_hash" type="string">
  Mot de passe haché de la connexion de l’utilisateur.

  Lors de la création des utilisateurs, Auth0 utilise [bcrypt](https://auth0.com/blog/hashing-in-action-understanding-bcrypt/) pour sécuriser les mots de passe. L’importation de mots de passe hachés permet aux utilisateurs de conserver leurs mots de passe pour une expérience plus fluide. Les mots de passe compatibles doivent être hachés à l’aide de bcrypt `$2a$` ou `$2b$` et utiliser 10 saltRounds.

  Cette propriété ne peut être fournie que lors de la première importation de l’utilisateur et ne peut pas être mise à jour par la suite.
</ResponseField>

<ResponseField name="custom_password_hash" type="object" post={ ["upsertable"] }>
  Une méthode plus générale pour fournir le hachage du mot de passe de l’utilisateur.

  Vous pouvez utiliser ce champ au lieu du champ `password_hash` lorsque le hachage du mot de passe de l’utilisateur a été créé avec un autre algorithme. Ce champ et `password_hash` sont mutuellement exclusifs.

  Lors de l’importation en bloc, vous pouvez mettre à jour le `custom_password_hash` si l’utilisateur ne s’est pas connecté à l’aide du `custom_password_hash` importé initialement.

  <Expandable title="enfants">
    <ResponseField name="algorithme" type="string" required>
      L’algorithme utilisé pour hacher le mot de passe.

      Auth0 prend en charge les algorithmes suivants :

      <Tabs>
        <Tab title="Argon2">
          Lorsque `algorithm` est défini sur [`argon2`](https://github.com/p-h-c/phc-winner-argon2) :

          * `hash.encoding` doit être `utf8`.
          * `hash.salt` n’est pas autorisé.
          * `hash.value` doit être au format de chaîne PHC, tel que défini dans [P-H-C / phc-string-format](https://github.com/P-H-C/phc-string-format/blob/master/phc-sf-spec.md) sur GitHub. Il doit également respecter les exigences définies dans [Auth0 / magic](https://github.com/auth0/magic#magicpasswordhash--magicverifypassword) sur GitHub.
          * `hash.value` doit inclure le salt encodé en base64 (tel que défini dans la documentation `PHC`).
        </Tab>

        <Tab title="bcrypt">
          Lorsque `algorithm` est défini sur [`bcrypt`](https://auth0.com/blog/hashing-in-action-understanding-bcrypt/) :

          * `hash.encoding` doit être `utf8`.
          * `hash.salt` est autorisé avec l’encodage et la position du sel.
          * `hash.value` doit inclure l’un de ces préfixes :

            * `$2a$`
            * `$2b$`
            * `$2y$`

            Les autres préfixes, comme `$2$`, `$sha1$` et `$2x$`, ne sont pas pris en charge pour le moment.

          Par exemple, cette valeur a été générée à partir de la chaîne `hello` avec un paramètre de coût de 10 : `$2b$10$nFguVi9LsCAcvTZFKQlRKeLVydo8ETv483lkNsSFI/Wl1Rz1Ypo1K`

          L’algorithme `bcrypt` traite au maximum 72 octets d’entrée lors du calcul ou de la comparaison des hachages de mots de passe, et la longueur de `salt.value` est prise en compte dans cette limite de 72 octets. Toute entrée qui dépasse cette limite est tronquée. Par exemple, si le sel occupe 10 octets, la longueur maximale du mot de passe pour le hachage ou la comparaison est de 62 octets.

          Les mots de passe qui dépassent cette limite réduite sont tronqués, ce qui peut affaiblir leur robustesse ou entraîner des collisions de hachage. Validez toujours la longueur des mots de passe avant le hachage.
        </Tab>

        <Tab title="HMAC">
          Lorsque `algorithm` est défini à [`hmac`](https://tools.ietf.org/html/rfc2104) :

          * `hash.encoding` doit être `hex` ou `base64`.
          * `hash.digest` est obligatoire et doit être l’un des suivants :
            * `md4`
            * `md5`
            * `ripemd160`
            * `sha1`
            * `sha224`
            * `sha256`
            * `sha384`
            * `sha512`
            * `whirlpool`
          * `hash.key.value` est obligatoire.
          * `hash.key.encoding` doit être `base64`, `hex` ou `utf8`.
        </Tab>

        <Tab title="LDAP">
          Lorsque `algorithm` est défini à [`ldap`](https://tools.ietf.org/html/rfc2307#section-5.3) (`RFC-2307 "userPassword"`) :

          * `hash.encoding` doit être `utf8`.
          * `hash.salt` n’est pas autorisé.
          * `hash.value` doit respecter le format décrit à la [section 5.3 de la RFC-2307](https://tools.ietf.org/html/rfc2307#section-5.3) sur IETF Datatracker.
          * Le schéma doit être l’un des suivants : `md5|smd5|sha*|ssha*`. Consultez [cette page](https://www.openldap.org/faq/data/cache/347.html) pour en savoir plus.
            Le schéma [crypt](https://www.openldap.org/faq/data/cache/344.html) n’est **pas pris en charge** en raison d’un comportement qui dépend du système et de la mise en œuvre. Pour en savoir plus, consultez [Open LDAP Admin Guide - 14.4.2. CRYPT password storage scheme](https://www.openldap.org/doc/admin24/guide.html#CRYPT%20password%20storage%20scheme).
        </Tab>

        <Tab title="MD et SHA">
          Lorsque `algorithm` est défini sur [`md4`](https://tools.ietf.org/html/rfc1320), [`md5`](https://tools.ietf.org/html/rfc1321), [`sha1`](https://tools.ietf.org/html/rfc3174), [`sha256`](https://tools.ietf.org/html/rfc4634) ou [`sha512`](https://tools.ietf.org/html/rfc4634) :

          * `hash.encoding` doit être égal à `hex` ou à `base64`.
        </Tab>

        <Tab title="PBKDF2">
          Lorsque `algorithm` est défini sur [`pbkdf2`](https://tools.ietf.org/html/rfc2898#section-5.2) :

          * `hash.encoding` doit être `utf8`.
          * `hash.salt` n’est pas permis.
          * `hash.value` devrait être au format de chaîne PHC, tel que spécifié dans [P-H-C / phc-string-format](https://github.com/P-H-C/phc-string-format/blob/master/phc-sf-spec.md) sur GitHub.
          * `hash.value` doit inclure le salt encodé en B64 (base64 sans les caractères de remplissage `=`, comme indiqué dans la documentation `PHC`).
          * `hash.value` devrait inclure les paramètres `i` (itérations) et `l` (longueur de clé). Si ces paramètres sont omis, les valeurs par défaut sont `i=100000` et `l=64`.
          * `id` devrait être au format `pbkdf2-<digest>` (`pbkdf2-sha512`, `pbkdf2-md5`, etc.). Les condensats pris en charge sont :
            * `RSA-MD4`
            * `RSA-MD5`
            * `RSA-MDC2`
            * `RSA-RIPEMD160`
            * `RSA-SHA1`
            * `RSA-SHA1-2`
            * `RSA-SHA224`
            * `RSA-SHA256`
            * `RSA-SHA384`
            * `RSA-SHA512`
            * `md4`
            * `md4WithRSAEncryption`
            * `md5`
            * `md5WithRSAEncryption`
            * `mdc2`
            * `mdc2WithRSA`
            * `ripemd`
            * `ripemd160`
            * `ripemd160WithRSA`
            * `rmd160`
            * `sha1`
            * `sha1WithRSAEncryption`
            * `sha224`
            * `sha224WithRSAEncryption`
            * `sha256`
            * `sha256WithRSAEncryption`
            * `sha384`
            * `sha384WithRSAEncryption`
            * `sha512`
            * `sha512WithRSAEncryption`
            * `ssl3-md5`
            * `ssl3-sha1`
            * `whirlpool`
        </Tab>

        <Tab title="scrypt">
          Lorsque `algorithm` est défini sur [`scrypt`](https://datatracker.ietf.org/doc/rfc7914/) :

          * `hash.encoding` doit être `hex` ou `base64`.

          <ResponseField name="keylen" type="integer" required>
            Longueur de clé souhaitée, en octets, pour le hachage scrypt. Doit être un entier supérieur à zéro.
          </ResponseField>

          <ResponseField name="cost" type="integer" default={16384}>
            Paramètre de coût CPU/mémoire utilisé pour le hachage scrypt. Doit être une puissance de deux supérieure à un.
          </ResponseField>

          <ResponseField name="blockSize" type="integer" default={8}>
            Paramètre de taille de bloc utilisé pour le hachage scrypt. Doit être un entier positif.
          </ResponseField>

          <ResponseField name="parallelization" type="integer" default={1}>
            Paramètre de parallélisation utilisé pour le hachage scrypt. Doit être un entier positif.
          </ResponseField>
        </Tab>
      </Tabs>
    </ResponseField>

    <ResponseField name="hachage" type="object" required>
      <Expandable title="children">
        <ResponseField name="value" type="string">
          Le hachage du mot de passe.
        </ResponseField>

        <ResponseField name="encoding" type="string">

        </ResponseField>

        <ResponseField name="digest" type="string">

        </ResponseField>

        <ResponseField name="key" type="object">
          La clé utilisée pour générer le hachage HMAC.

          <Expandable title="children">
            <ResponseField name="value" type="string" required>
              La valeur de la clé.
            </ResponseField>

            <ResponseField name="encoding" type="string" default="utf8">

            </ResponseField>
          </Expandable>
        </ResponseField>
      </Expandable>
    </ResponseField>

    <ResponseField name="sel" type="object">
      <Expandable title="children">
        <ResponseField name="value" type="string" required>
          La valeur du salt utilisée pour générer le hachage.
        </ResponseField>

        <ResponseField name="encoding" type="string" default="utf8">
          L’encodage du salt fourni. Doit être l’un des suivants : <ul><li>`base64`</li><li>`hex`</li><li>`utf8`</li></ul> Les variantes hexadécimales en majuscules et en minuscules sont prises en charge, de même que le base64 encodé pour les URL.
        </ResponseField>

        <ResponseField name="position" type="string" default="prefix">

    <ResponseField name="mot de passe" type="object">

  </Expandable>

  <Expandable title="enfants">

    <ResponseField name="phone" type="object">
      <ResponseField name="phone.value" type="string" required>

      </ResponseField>

      <ResponseField name="totp.secret" type="string" required>

      </ResponseField>
