title: Mettre à jour les profils utilisateur à l’aide de votre base de données
---

Mettez à jour les profils utilisateur lorsque vous [utilisez votre propre base de données comme fournisseur d’identité](/docs/fr-ca/authenticate/database-connections/custom-db) en effectuant les tâches suivantes :

* Utilisez la [Management API](https://auth0.com/docs/api/management/v2#!/Users/patch_users_by_id).
* Mettez à jour l’utilisateur dans votre base de données.
* [Configurez la migration des utilisateurs](/docs/fr-ca/manage-users/user-migration/configure-automatic-migration-from-your-database) de votre base de données vers Auth0.

<div id="update-users-with-the-management-api">
  ## Mettre à jour les utilisateurs avec la Management API
</div>

Lorsque vous utilisez votre propre base de données pour l’authentication, vous pouvez utiliser la [Management API](https://auth0.com/docs/api/management/v2) pour mettre à jour les champs suivants :

* `app_metadata`
* `user_metadata`
* `blocked`

Si vous devez mettre à jour d’autres champs utilisateur, vous devrez le faire directement dans votre base de données.

<div id="update-users-in-your-database">
  ## Mettez à jour les utilisateurs de votre base de données
</div>

Vous pouvez mettre à jour les profils utilisateur dans votre base de données comme vous le faites habituellement, et Auth0 mettra à jour le profil utilisateur en cache la prochaine fois que cet utilisateur se connectera.

Le profil utilisateur dans la base de données personnalisée peut utiliser n’importe quelle structure de profil utilisateur, mais vous devez le mapper dans la requête Login vers les attributs du profil utilisateur normalisé d’Auth0, comme illustré dans le modèle « Login » de la base de données personnalisée.

Vous pouvez accéder aux modèles de base de données personnalisée via
Connections -&gt; Database -&gt; Custom Database. Assurez-vous d’activer la bascule « Use my own database » pour permettre la modification des scripts.

Consultez la section [Cache du profil utilisateur](#user-profile-cache) ci-dessous pour un bref aperçu de la façon dont Auth0 met les profils utilisateur en cache.

<div id="update-users-through-migration">
  ## Mettre à jour les utilisateurs par migration
</div>

Si vous avez [activé la migration des utilisateurs](/docs/fr-ca/manage-users/user-migration/configure-automatic-migration-from-your-database) et qu’un utilisateur a déjà été migré vers la base de données Auth0, Auth0 n’interrogera plus votre base de données pour obtenir le profil utilisateur. Par conséquent, les modifications apportées à la base de données personnalisée pour cet utilisateur ne seront jamais répercutées dans Auth0.

Une fois qu’un utilisateur a été migré, vous pourrez aussi mettre à jour des champs comme `name`, `nickname`, `given_name`, `family_name`, `picture`, `email` et `email_verified` au moyen de la <Tooltip tip="Management API : un produit qui permet aux clients d’effectuer des tâches administratives." cta="Voir le glossaire" href="/docs/fr-ca/glossary?term=Management+API">Management API</Tooltip>.

Toutefois, les règles de mise à jour des autres champs utilisateur continueront de s’appliquer, comme indiqué dans le [Profil utilisateur normalisé](/docs/fr-ca/manage-users/user-accounts/user-profiles/normalized-user-profiles).

<div id="user-profile-cache">
  ## Cache du profil utilisateur
</div>

Auth0 met en cache le profil utilisateur reçu d’une [connexion de base de données](/docs/fr-ca/authenticate/database-connections) avant de l’envoyer à l’application cliente. Ce cache est stocké dans la base de données d’Auth0 et est actualisé chaque fois que l’utilisateur s’authentifie.

Les valeurs mises en cache des champs du [profil utilisateur normalisé](/docs/fr-ca/manage-users/user-accounts/user-profiles/normalized-user-profile-schema) sont basées sur les valeurs renvoyées par le script Login de votre connexion de base de données personnalisée.

Le profil utilisateur est mis en cache pour plusieurs raisons. D’abord, la mise en cache vous permet d’implémenter l’[authentification unique (SSO)](/docs/fr-ca/authenticate/single-sign-on) dans la couche Auth0 afin d’éviter de solliciter la connexion pour chaque requête. De plus, cela assure une meilleure résilience si une connexion est temporairement indisponible.
