Auth0 Experiment Center est un moteur d&#39;expérimentation natif d&#39;Auth0. Il vous permet de tester en mode A/B les modifications apportées à votre expérience d&#39;[authentification](/docs/fr-ca/authenticate/login/auth0-universal-login) et d&#39;en mesurer les répercussions dans vos [journaux](/docs/fr-ca/deploy-monitor/logs) d&#39;événements d&#39;authentification.

Avec Experiment Center, vous définissez votre test A/B dans Auth0, le trafic est réparti de façon déterministe et vos événements d&#39;authentification existants vous sont retournés enrichis de métadonnées d&#39;expérimentation, ce qui vous permet d&#39;en analyser les résultats dans vos propres outils.

Experiment Center fait partie de la [Auth0 Identity Conversion Suite](/docs/fr-ca/customize/identity-conversion-suite).

## Fonctionnement {#how-it-works}

Experiment Center vous permet de réaliser des tests A/B contrôlés sur votre pipeline d&#39;authentification Auth0. Plutôt que de déployer un changement à tous les utilisateurs d&#39;un coup, vous exposez le nouveau comportement à un pourcentage contrôlé du trafic, vous mesurez le résultat à l&#39;aide d&#39;événements d&#39;authentification enrichis, puis vous promouvez le gagnant au moment opportun.

Experiment Center s&#39;articule autour de trois entités :

* **Expérimentation** : définit la façon dont le trafic est réparti et le moment où le test s&#39;exécute.
* **Indicateur de fonctionnalité** : définit ce que vous testez ainsi que les variations possibles.
* **Segment** : définit un ensemble de règles permettant d&#39;acheminer les expérimentations vers des variations précises.

<Warning>
  Le client doit veiller à n&#39;utiliser les fonctionnalités liées aux témoins et aux technologies similaires qu&#39;à des fins strictement nécessaires à la prestation de ses services à ses utilisateurs finaux.

  Pour en savoir plus, consultez [Conformité d&#39;Auth0 au Règlement général sur la protection des données](/docs/fr-ca/secure/data-privacy-and-compliance/gdpr).
</Warning>

## Expérimentation {#experiment}

Une expérimentation est une couche de mesure qui englobe un indicateur de fonctionnalité. Elle définit :

* Quel indicateur de fonctionnalité est mis à l&#39;essai
* Comment le trafic est réparti entre les variations
* À quel moment le test se déroule

Chaque expérimentation renvoie à un seul indicateur de fonctionnalité.

### Cycle de vie d&#39;une expérimentation {#experiment-lifecycle}

Les expérimentations comportent cinq états :

| Statut      | Signification                                                                                                                              |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `draft`     | Créée, mais non démarrée. Peut être testée sans risque au moyen de remplacements par paramètre de requête.                                 |
| `active`    | En cours. L&#39;attribution des variantes et l&#39;injection de contexte sont actives pour toutes les transactions d&#39;authentification. |
| `paused`    | Suspendue temporairement. Aucune nouvelle attribution. Les sessions en cours conservent la variation qui leur a été attribuée.             |
| `completed` | Terminée. Aucune nouvelle attribution. La configuration est conservée à titre de référence lors de la promotion manuelle.                  |
| `archived`  | Supprimée de façon réversible. Masquée des vues de liste par défaut. Les données analytiques sont conservées.                              |

### Stratégies d&#39;allocation {#allocation-strategies}

Une expérimentation utilise l&#39;une des deux stratégies d&#39;allocation suivantes :

**Par pourcentage :** le trafic est réparti entre les variations selon un poids. La somme de tous les poids doit être égale à 100. Un poids de 0 est valide (la variation figure dans la définition de l&#39;expérimentation, mais ne reçoit aucun trafic).

**Par segment (ciblée) :** le trafic est acheminé vers les variations selon l&#39;appartenance à un segment. Les segments sont évalués par ordre de priorité et le premier segment correspondant l&#39;emporte. Si aucun segment ne correspond, c&#39;est l&#39;allocation `is_fallback` qui reçoit la requête.

Pour en savoir plus sur l&#39;entité expérimentation, consultez [Détails des entités](/docs/fr-ca/customize/experiment-center/entities#experiment).

### Contexte d&#39;expérimentation {#experiment-context}

Lorsqu&#39;une expérimentation est active et qu&#39;une variation est attribuée, Experiment Center injecte un objet `ExperimentContext` dans vos surfaces d&#39;exécution.

Les écrans [ACUL](/docs/fr-ca/customize/login-pages/advanced-customizations#advanced-customizations-for-universal-login-acul) le reçoivent uniquement si vous les y inscrivez au moyen de `context_configuration`.
Pour en savoir plus, consultez le [guide d&#39;intégration ACUL](/docs/fr-ca/customize/experiment-center/integrations/acul-integration-guide).

Les [Actions](/docs/fr-ca/customize/actions/actions-overview) et les [gabarits de page](/docs/fr-ca/customize/login-pages/universal-login/customize-templates#customize-universal-login-page-templates) le reçoivent automatiquement dès qu&#39;une expérimentation est active. Voici la structure de l&#39;objet :

```typescript
{
  experiment_id: string;   // Identifiant de l'expérimentation active
  variation_id: string;    // Identifiant de la variation attribuée
  config: {                // Configuration fusionnée (référence + remplacements)
    [paramName]: { value: unknown }
  };
  is_control: boolean;     // Vrai s'il s'agit de la variation de contrôle
}
```

Le champ `config` contient la configuration fusionnée complète de la variation attribuée. Chaque paramètre défini dans l&#39;indicateur de fonctionnalité a toujours une valeur. Vous n&#39;avez donc pas à écrire de logique de repli.

### Assignation {#assignment}

Une assignation détermine comment un utilisateur est acheminé vers une variation précise durant une transaction d&#39;authentification. Les assignations sont déterministes et persistantes : un même utilisateur voit toujours la même variation pour la même expérimentation sur le même appareil, ce qui assure la stabilité de son expérience d&#39;une connexion à l&#39;autre.

* **L&#39;allocation par pourcentage** répartit le trafic entre les variations selon leur pondération. Un sujet donné est toujours assigné à la même variation.
* **L&#39;allocation par segment** évalue les propriétés de la requête au regard de vos règles de segment, par ordre de priorité. Le premier segment correspondant détermine la variation, et une requête qui correspond au même segment aboutit toujours à la même variation.

Les résultats d&#39;assignation sont consignés dans les journaux de votre locataire sous `details.experiment`; ils ne sont pas exposés par une API distincte.

Pour en savoir plus sur l&#39;entité d&#39;assignation, consultez [Détails des entités](/docs/fr-ca/customize/experiment-center/entities#assignment).

## Indicateur de fonctionnalité {#feature-flag}

Un indicateur de fonctionnalité est l&#39;unité de contrôle de ce qui est testé. Il contient :

* Une **configuration de référence** : des paramètres typés et leurs valeurs par défaut
* Une ou plusieurs **variations** : des configurations différentes de la référence

Les indicateurs de fonctionnalité sont propres à un locataire et réutilisables. Un même indicateur peut servir à plusieurs expérimentations au fil du temps (par exemple, un test au T1 et un ajustement au T2 pour la même fonctionnalité).

### Cycle de vie d&#39;un indicateur de fonctionnalité {#feature-flag-lifecycle}

Les indicateurs de fonctionnalité ont un cycle de vie enregistré qui comporte trois états :

| Statut     | Signification                                                                                                           |
| ---------- | ----------------------------------------------------------------------------------------------------------------------- |
| `draft`    | Créé, mais pas encore actif. Ne peut pas être référencé par une expérimentation active.                                 |
| `active`   | Prêt à l&#39;emploi. Requis avant qu&#39;une expérimentation référençant cet indicateur puisse être activée.            |
| `archived` | État terminal. Aucune nouvelle expérimentation ne peut référencer cet indicateur. Créez un nouvel indicateur au besoin. |

Pour en savoir plus sur l&#39;entité indicateur de fonctionnalité, consultez [Détails des entités](/docs/fr-ca/customize/experiment-center/entities#feature-flag).

### Variation {#variation}

Une variation est une version de l&#39;expérience définie dans un indicateur de fonctionnalité. Elle précise quels paramètres de configuration diffèrent de la référence, et dans quelle mesure.

* La **variation de contrôle** constitue la référence; ses remplacements sont vides (aucun paramètre n&#39;est modifié par rapport aux valeurs par défaut de l&#39;indicateur).
* Les **variations de traitement** précisent chacune un ou plusieurs remplacements de paramètres.

Les variations ne comportent pas de marqueur `is_control`. C&#39;est au niveau de l&#39;allocation, et non de la variation, qu&#39;on détermine si une variation sert de contrôle statistique pour une expérimentation donnée. Une même variation peut être le contrôle dans une expérimentation et un traitement dans une autre.

Pour en savoir plus sur l&#39;entité variation, consultez [Entities Details](/docs/fr-ca/customize/experiment-center/entities#variation).

## Segment {#segment}

Un segment est un groupe nommé de requêtes d&#39;authentification qui correspondent à un ensemble de règles. Vous utilisez les segments dans les expérimentations à allocation ciblée pour diriger des cohortes de trafic précises vers des variations précises.

Les segments sont limités au locataire et réutilisables d&#39;une expérimentation à l&#39;autre.

Pour en apprendre davantage sur l&#39;entité segment, consultez [Détails des entités](/docs/fr-ca/customize/experiment-center/entities#segment).
